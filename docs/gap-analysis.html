Frontend Deep Dive (STEP 5)

1. Simple analogy

The backend is a kitchen. It cooks food (runs the routing logic, calls the LLMs, saves the receipt to a ledger). The frontend — streamlit_app.py — is the waiter. The waiter never cooks. It walks to your table, takes your order (a prompt typed into a text box), carries it to the kitchen (an HTTP call to POST /chat), and brings back whatever the kitchen made, plated nicely (the routing tier badge, the cost breakdown, the quality verdict — all rendered from the same JSON chat.py already returns).

2. Real-world problem

Someone needs to actually *use* this system without curling JSON by hand. And demos need to look trustworthy — a routing decision nobody can see is just a black box; a routing decision with a visible "why" builds confidence in the product.

3. How this project solves it

One Streamlit process, one Python file, four "pages" that are really just four Python functions (render_chat, render_history, render_analytics, render_settings) picked by a sidebar radio button. Every page does the same three things: call one backend endpoint via httpx, get JSON back, render it as styled HTML cards. No page ever talks to the database directly, no page ever imports anything from backend/ — it is a pure HTTP client, exactly the same as if it were written in JavaScript instead of Python.

4. Actual implementation

flowchart TD
    A["User types prompt, clicks Send<br/>render_chat()"] --> B["_request_with_retry POST /api/chat"]
    B --> C["httpx.request against BACKEND_URL"]
    C -->|"200 JSON"| D["st.container renders Response card"]
    C -->|"cold-start HTML page, not JSON"| E["retry loop: show 'waking up' message, sleep 4s"]
    C -->|"real timeout, retry_on_timeout=False"| F["st.error: not resubmitted, avoid duplicate billing"]
    C -->|"our API's own error JSON"| G["st.error(data['detail'])"]
    D --> H["Routing Decision card + Cost card + Quality card<br/>built from kv_row() / tier_badge() / quality_badge()"]

_request_with_retry() — the one genuinely interesting function in this file. It exists because this app is deployed on Render's free tier, which puts the container to sleep after inactivity. The very next request has to wait for a cold start — and Render's own "waking up" placeholder page comes back as HTML, not JSON, almost instantly. That's the signal this function keys on: resp.json() raising ValueError means "that wasn't our API answering, that was the platform's wake-up page" → retry. A 200 with real JSON, or a 4xx/5xx with a detail field, means the *backend itself* answered → stop retrying and show it.

The other real decision here: retry_on_timeout=False for POST /chat specifically. If a request to /chat times out client-side, the backend might still be mid-flight, possibly about to make a real, billed call to DeepSeek R1 that takes 140 seconds. Silently retrying would risk paying for the same prompt twice. Every other endpoint (GET /history, GET /stats, GET /models) is safe to retry — they're read-only, retrying them costs nothing and fixes nothing worse than a wasted network round trip.

Session state: there isn't much. Streamlit reruns the *entire script top to bottom* on every interaction (every click, every text input) — this is how Streamlit works, not something this codebase built. There's no st.session_state usage anywhere in this file; every page just re-fetches from the backend on every rerun. This is a deliberate simplicity trade-off worth naming in an interview: it means the UI is always showing fresh data, at the cost of an HTTP round-trip on every single interaction, even ones that didn't change any backend state (e.g., typing in the search box on the History page re-runs the whole script, though the actual filtering (df[df["prompt"].str.contains(...)]) happens client-side on the already- fetched pandas DataFrame, not as a new API call).

Error handling, concretely: three distinct failure shapes are distinguished — a network-level httpx.HTTPError, a client-side timeout, and an API-level error response — and each gets different UI treatment (silent retry, "please try again" without retry, or st.error(detail) respectively).

5. Interview explanation

"The frontend is a stateless HTTP client. It calls its own backend through a small retry wrapper that has to solve one real problem: distinguishing 'the free-tier host is asleep, keep trying' from 'the backend actually rejected this' from 'this specific call already reached the server and must not be silently resent.' Everything else — cards, badges, charts — is just formatting the JSON chat.py already returns."

6. Mini summary

streamlit_app.py = 4 page functions × (1 API call + JSON-to-HTML rendering). theme.py = the CSS and tiny HTML-snippet helpers those pages call. The one piece of real logic is _request_with_retry's cold-start detection and its refusal to retry a possibly-in-flight paid LLM call.

theme.py — the other frontend file

1. Analogy: if streamlit_app.py is the waiter taking orders, theme.py is the uniform and the restaurant's interior design — it makes no decisions about what food goes where, it just makes everything look consistent.

2. Problem: Streamlit's default look is plain and doesn't have a rich enough built-in theming API for a custom, card-based design.

3. Solution: one big CSS string, injected once via st.markdown(CSS, unsafe_allow_html=True), plus small Python functions (metric_tile, tier_badge, quality_badge, kv_row, page_header) that return pre-styled HTML snippets so streamlit_app.py never has to write raw <div class="..."> strings inline.

4. One thing worth knowing precisely: div.st-key-response_card is targeted very specifically (not the generic stVerticalBlockBorderWrapper test ID) because that generic ID is *reused by Streamlit's own page layout* — targeting it globally would have boxed the entire page in a border, not just the one response card. This is a real, documented CSS-scoping gotcha in the file's own comment, and a good example of "read the actual DOM before you write a selector."

5. Interview explanation: "It's a design-tokens file — colors, badge/card HTML builders — split out purely so the 400-line page-logic file doesn't also carry 200 lines of CSS."

6. Mini summary: Pure presentation. Zero business logic. Skippable past a five-minute skim.

Deployment Deep Dive (STEP 6)

1. Simple analogy

Think of shipping this app like moving into a furnished apartment building with three roommates who each do one job, and a doorman out front who decides which roommate gets which visitor. The doorman is nginx. Two of the roommates are FastAPI and Streamlit, each running as their own process, each only reachable from inside the building (127.0.0.1), never directly from the street. The building itself is one Docker container — all three of them move in together, packed by the Dockerfile, and the building's front door is the *one* public port Render exposes.

2. Real-world problem

You have two different servers (an API and a UI) that both need to be reachable from the internet, but a typical free-tier host (Render, in this case) gives you exactly one public port per service. You also don't want to run two separate paid services for one demo app.

3. How this project solves it

One container, three processes, one public port. deploy/start.sh boots FastAPI on 127.0.0.1:8000 and Streamlit on 127.0.0.1:8501 as background processes, then runs nginx in the foreground as the container's main process — nginx is the thing Docker/Render actually watches to decide if the container is alive. deploy/nginx.conf.template is nginx's routing table: anything starting with /api/ goes to FastAPI (with the /api prefix *stripped*, so backend/routers/chat.py's /chat route never has to know it's being proxied under /api/chat from the browser's point of view); everything else goes to Streamlit, including the WebSocket upgrade headers Streamlit's live UI needs to stay connected.

4. Actual implementation

Environment variables — where they actually come from: render.yaml declares which env vars the Render service needs (GOOGLE_API_KEY, OPENROUTER_API_KEY, DATABASE_URL — all sync: false, meaning Render won't auto-populate them, a human sets them in the dashboard; plus LOG_LEVEL, EASY_MAX_WORDS, MEDIUM_MAX_WORDS with real default values baked into the YAML). These become real environment variables inside the container, which backend/utils/config.py's Settings class picks up automatically (pydantic-settings reads .env *or* real env vars — env vars take precedence, which is exactly what production needs since there's no .env file inside a deployed container).

$PORT specifically: Render assigns this dynamically at runtime — it's not fixed at 8080. nginx.conf.template has listen ${PORT}; literally as a placeholder string; start.sh runs envsubst '${PORT}' to substitute the real value into a generated /etc/nginx/nginx.conf before nginx starts. Note the explicit '${PORT}' argument to envsubst — without it, envsubst would try to substitute *every* $variable-looking token in the file, including nginx's own $host, $http_upgrade, and $remote_addr, which are nginx's runtime variables, not shell variables, and would break if replaced with empty strings.

Static files: none exist in this project — Streamlit serves its own UI dynamically, there's no separate static asset pipeline.

Local dev (docker-compose.yml) vs. production (render.yaml): docker-compose.yml builds the same Dockerfile locally, maps port 8080, and mounts a ./data volume (for local SQLite persistence across container restarts). render.yaml is Render-specific IaC — same Dockerfile, but declares the platform-level concerns (healthCheckPath: /api/health, plan: free) that only matter in that hosting context.

5. Interview explanation

"Single-container, multi-process deployment: nginx as a reverse proxy in front of FastAPI and Streamlit, each bound to localhost-only ports inside the container. Path-based routing (/api/* vs everything else) means the browser only ever sees one origin. start.sh is the process supervisor — crude compared to something like supervisord, but sufficient for exactly two background processes and one foreground one."

6. Mini summary

Dockerfile builds the image. start.sh boots three processes and hands control to nginx. nginx.conf.template is the routing table, filled in with the real port at container start via envsubst. render.yaml / docker-compose.yml are two different platforms' instructions for running that same image.

STEP 7 — Test Suite Deep Dive, Grouped by Feature

API contract stability (test_api_regression.py)

What it validates: that /chat, /history, /stats, /analytics/*, /routing/decision/{id}, and /agent/* all return *exactly* the field set they're supposed to (EXPECTED_CHAT_KEYS, EXPECTED_HISTORY_KEYS, EXPECTED_STATS_KEYS — literal set comparisons against response.json().keys()), end-to-end through a real TestClient(app), with every LLM/provider call faked via app.dependency_overrides and monkeypatch. Why it exists: this file's own docstring says it — regression coverage for the refactor from one flat RequestLog table to the current four-table normalized schema. The API's *external contract* had to survive that internal rewrite unchanged. What bug it prevents: silently dropping or renaming a response field during a future refactor — a mistake that wouldn't show up as a crash, only as a frontend field quietly rendering blank. What it protects: the entire routers/ layer, transitively.

Classifier JSON parsing (test_classifier_json_format.py)

What it validates: strip_json_fence() correctly strips a `json fence and passes plain JSON through unchanged; and OpenRouterProvider.generate() actually sends {"response_format": {"type": "json_object"}} when asked, and omits it for regular (non-structured) chat calls. Why it exists: a real production incident. The module docstring states it plainly: the classifier and quality verifier were silently dead in production because Mistral (via OpenRouter) wrapped its JSON reply in a markdown fence, and OpenRouterProvider wasn't requesting response_format="json_object" — every real call failed to parse and silently fell back to the heuristic classifier, with nobody noticing because the fallback path doesn't error, it just degrades. What bug it prevents: this exact regression happening again, silently, a second time. What it protects: classifier_service.py, quality_verifier.py, openrouter_provider.py — this is the single best "tell me about a real bug" story in the entire codebase.

Decision Card reconstruction (test_decision_card.py)

What it validates: get_decision_card() across six cases — unknown request_id → None; normal routing with no recommendation; an escalated decision's reasoning_steps correctly mention the escalation; a matching recommendation surfaces; a recommendation with a different policy_version is correctly ignored; a recommendation with a different provider/model is correctly ignored; and full JSON serialization shape. Why it exists: the matching logic in _find_matching_recommendation() (five-column exact equality, no FK) is exactly the kind of logic that's easy to get subtly wrong — this test suite exercises the specific "almost matches but doesn't" cases explicitly, not just the happy path. What bug it prevents: a recommendation from a stale policy or a different model silently attaching itself to the wrong decision card.

Transactional persistence (test_decision_service.py)

What it validates: record() writes all four tables correctly; quality_results is correctly skipped when no verdict was computed; and — the most important one — re-using a request_id raises IntegrityError and leaves no partial rows behind across any of the four tables. What bug it prevents: a partial write (e.g., Request inserted but RoutingDecision silently failing) that would corrupt the audit trail's guarantee that every requests row has a matching routing_decisions row.

The Investigation Agent (test_routing_agent.py)

What it validates: empty-database behavior (no findings, risk="low"); that investigate() genuinely never writes to routing_patterns or optimization_recommendations (the safety rule from routing_agent.py's own docstring, tested directly by asserting row counts don't change); degraded-task-type detection with a real 5-sample group; cost-anomaly detection using deliberately backdated rows to simulate a multi-day cost trend; recommendation validation both when live data still supports a recommendation ("trustworthy") and when live data has since reversed ("should be re-reviewed"); persistence and retrieval round-trip; JSON serialization shape. What bug it prevents: any of the five finding functions silently writing to a table they shouldn't, or a stale recommendation being reported as still-valid when live traffic has already contradicted it.

The Learning Pipeline (test_routing_learning.py)

What it validates: one pattern row per group with correct sample_size/pass_rate/failure_rate; refresh() is idempotent (calling it twice yields the same one row, not two); a recommendation is generated when an alternative model has a meaningfully better pass rate at sufficient sample size; patterns from a *different* policy_version never generate a cross-policy recommendation; no recommendation is generated below min_sample_size. What bug it prevents: exactly the "policy_version blending" bug described in routing_learning.py's own docstring — a recommendation being generated by comparing data across two different routing policies that were never actually in competition with each other.

Analytics aggregation (test_analytics_service.py)

What it validates: get_routing_overview() correctly aggregates by provider, model, task type, and tier, and computes average_cost and pass_rate correctly across a small, deliberately-constructed 2-row dataset (reuses test_routing_learning.py's _record() helper — a nice example of test code reuse mirroring the read/write service split in the app code itself). Also covers the empty-database case for every /analytics/* read endpoint. What bug it prevents: an aggregation query silently producing wrong averages (a classic SQL GROUP BY mistake) going undetected because it "looks" like reasonable output.

Bootstrap script (test_bootstrap_db.py)

What it validates: bootstrap() creates all 8 expected tables; and running it twice seeds routing_policies exactly once, not twice — the idempotency the script's own docstring promises. What bug it prevents: a re-run of the bootstrap script (e.g., during a redeploy) accidentally duplicating the seeded policy row.

STEP 8 — Small Files

backend/schemas/quality.py

Why it exists: QualityVerdict is the one-and-only structured shape the quality-judge LLM must return ({"passed": bool, "reason": str}). Tiny, but it's the schema that turns an untrusted LLM string into something quality_verifier.py can trust via .model_validate() — same role RoutingDecision plays for the classifier, just simpler.

backend/schemas/history.py

Why it exists: HistoryItem is the one response row shape for GET /history. Worth noting (already flagged in the Walkthrough's Code Smells section): several fields here (reasoning_level, classifier_model, classifier_cost, fallback_used) are always empty defaults in practice, because history_service.py has no persisted column to fill them from — the schema promises more than the data currently supplies.

backend/schemas/stats.py

Why it exists: StatsResponse — one flat object, GET /stats's entire response shape. No nested objects, because /stats is a dashboard summary, not a detail view.

backend/schemas/analytics.py

Why it exists: the largest of the small schema files — six response models (ProviderStats, ModelStats, TaskTypeStats, DailyMetric, RoutingOverviewResponse, RoutingPatternResponse, RecommendationResponse, RefreshResult) because /analytics/* has the most varied response shapes of any router (one overview object nesting three different stat-row types, plus two standalone list endpoints). Its own docstring makes a small but real design point: tier_distribution is typed as a plain dict[str, int] rather than a dedicated model, because its keys are always exactly the three known RoutingTier values — not "stringly typed," a deliberately fixed 3-key lookup.

backend/schemas/investigation.py

Why it exists: Evidence, Finding, SuggestedAction, InvestigationReport, InvestigationReportSummary — the typed shape of everything routing_agent.py produces. Worth reading Evidence's docstring once: it's explicitly a *pointer* to source data plus derived numbers, never a full copy of the underlying row — same anti-duplication principle as DecisionCard not storing a JSON blob.

deploy/start.sh, deploy/nginx.conf.template, Dockerfile,

docker-compose.yml, render.yaml

Covered fully in Step 6.

.streamlit/config.toml

Three brand colors (primaryColor, backgroundColor, secondaryBackgroundColor) plus textColor and gatherUsageStats = false. This is why the sidebar radio button's selected-dot color matches the theme even though theme.py's CSS injection can't reliably override it (per theme.py's own comment) — Streamlit's *native* theme engine reads this file directly.

requirements.txt

One line worth knowing cold for an interview: numpy==1.26.4 and pyarrow==17.0.0 are pinned explicitly, not left to resolve automatically, because an unpinned numpy once resolved to a version that segfaulted inside pyarrow's pandas-conversion code — the exact path st.dataframe() (used on the History page) exercises. This was confirmed with PYTHONFAULTHANDLER=1, not guessed. It's a genuinely good example of "a pin isn't superstition, it's a fix for a specific crash" — a strong answer to "tell me about a dependency issue you debugged."

The eight empty __init__.py files

They exist because Python's package system needs *a* file present in a directory (even an empty one) for that directory to be importable as a package (from backend.services import decision_service requires backend/, backend/services/, etc. to each have an __init__.py). There is genuinely nothing else to say about any of them.
