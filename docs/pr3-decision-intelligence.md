# PR 3: Decision Intelligence & Recommendation Surface

Adds `GET /routing/decision/{request_id}`: a deterministic, human-readable
explanation of one past routing decision, plus whether an optimization
recommendation (PR2) applies to it. Routing itself is completely
untouched — this PR only reads what PR1/PR2 already persist.

## How DecisionCards are built

`DecisionCard` used to be built once, at request time, inside
`DecisionService.record()` (PR1). PR3 replaces that with
`decision_service.get_decision_card(db, request_id)`, which builds the
card **on read**, from a join of `requests` + `routing_decisions` +
`execution_results` (all written transactionally by `record()` — see
PR1's doc), plus a lookup against `optimization_recommendations` (PR2).

There is no LLM in this path. `reasoning_steps` is assembled from columns
that were already there:

1. `task_type` (from the classifier's structured output, PR1)
2. `classifier_confidence` and `classifier_tier` (was this decision
   trustworthy at first read?)
3. Either "Selected `<tier>` tier" or, if `escalation_reason` is set,
   "Escalated to `<tier>` tier — `<reason>`" — reusing the exact string
   `routing_engine.py` generated for `RoutingResult.reasons`
4. "`<tier>` tier maps to `<provider>/<model>` under policy
   `<policy_version>`" — the routing.yaml lookup that actually happened
5. "Final routing complete"

Every step is a direct read or string interpolation of a persisted
value — nothing is inferred, summarized, or generated by a model. Two
decisions with identical `routing_decisions` rows produce byte-identical
`reasoning_steps` every time `get_decision_card()` is called.

## Why recommendations never affect routing

`get_decision_card()` only *reads* `optimization_recommendations` — it
never writes to it, to `routing_decisions`, or to `routing.yaml`. A match
sets `recommendation_available=True` and `recommendation_id` on the
`DecisionCard`, and the endpoint additionally resolves that ID into a
full `RecommendationSummary` in its response. That's the entire effect:
information surfaced to whoever reads the API response. There is no
code path anywhere in this PR — or any prior one — that lets a
recommendation change what `routing_engine.select()` returns. Applying a
recommendation still means a human edits `routing.yaml`'s tiers and
bumps `policy_version`, same as PR1/PR2 established.

## How policy_version isolates recommendations

`_find_matching_recommendation()` requires an exact match on
`policy_version`, `task_type`, `task_subcategory`, `current_provider`,
and `current_model` — not just provider/model. This reuses the same
attribution PR2's `routing_learning.py` already enforces when generating
recommendations (`docs/pr2-analytics.md`): a recommendation generated
under policy `v1.0` can never surface on a decision made under `v2.0`,
even if the provider/model happen to coincide. Without the
`policy_version` match, a stale recommendation from before a policy
change could look "available" on a request that was never evaluated
under that recommendation's evidence.

## How future agentic optimization will consume DecisionCards

The Routing Optimization Agent (PR4) is scoped to read
`GET /routing/decision/{request_id}` and `GET /analytics/recommendations`
— it does not get write access to routing state, and DecisionCards are
exactly the structured, LLM-free evidence it needs to reason over without
re-deriving anything from raw rows itself. Because `reasoning_steps` and
`RecommendationSummary.summary` are already plain strings (not raw
numbers the agent would have to interpret), the agent's own output can
quote them directly instead of re-summarizing, which keeps its answers
traceable back to a specific persisted decision.

## What's deliberately not here

- No new database table. `DecisionCard` is assembled from PR1's four
  tables plus PR2's `optimization_recommendations` — reusing a
  `RoutingDecision` row and one recommendation lookup fully covers every
  field the spec asked for.
- No caching of `get_decision_card()` results — it's a point lookup by
  primary key across small joins, not a scan; add caching only if a real
  access pattern ever makes it a bottleneck.
- `DecisionCard` is not attached to `POST /chat`'s response. It's
  reachable by `request_id` via `GET /routing/decision/{id}` right after
  a chat call, which keeps `/chat`'s response contract exactly what PR1's
  regression tests pin it to.
