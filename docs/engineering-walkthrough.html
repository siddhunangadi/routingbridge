RoutingBridge — Engineering Walkthrough Guide

This is the implementation guide, not the architecture guide. It assumes you've read docs/backend-architecture.md and already know the shape of the system. This document is about the *code*: which file to open first, what each function actually does, and where the sharp edges are.

Everything below is derived directly from backend/, config/, scripts/, and tests/ as they exist in this repository. Nothing is inferred or invented — where the code doesn't do something (retries, auth, caching), this guide says so explicitly instead of describing a feature that isn't there.

1. Reading Order

Read these in this order, not randomly:

  1. backend/main.py
  2. backend/routers/chat.py
  3. backend/schemas/chat.py, routing_decision.py, routing.py
  4. backend/services/classifier_service.py, heuristic_classifier.py, routing_engine.py
  5. backend/services/providers/base.py, factory.py, gemini_provider.py, openrouter_provider.py
  6. backend/database/db.py, models.py
  7. config/routing.yaml, config/pricing.yaml, backend/utils/config.py, yaml_config.py, startup_validation.py
  8. tests/conftest.py, tests/test_failure_paths.py

Why this order and not another: main.py is four lines of real logic wrapped in FastAPI ceremony — it tells you what routers exist and that config validation happens at boot, nothing more. chat.py is the one file that touches every other subsystem in a single, linear function, so reading it first gives you a map of the whole system before you've read any of the individual pieces — you'll recognize classifier_service, routing_engine, providers, and decision_service by name before you open any of them. Schemas next because chat.py is full of type names (RoutingDecision, RoutingResult, ChatResponse) that are meaningless until you've seen their field lists. Services in call order (classifier → engine → provider) mirrors the actual request flow. Database last-but-one because until you've seen the services that write to it, the four-table split (requests / routing_decisions / execution_results / quality_results) looks like arbitrary normalization instead of "one insert per pipeline stage." Config files last because they're inert data — they only make sense once you know who reads them (classifier_service reads classifier:, routing_engine reads tiers:, cost_estimator reads pricing.yaml). Tests are the reading order's answer key: test_failure_paths.py specifically exercises every non-happy-path branch in chat.py, so it's the fastest way to confirm you understood the error handling correctly.

Everything else (the other 7 routers, analytics_service.py, routing_learning.py, routing_agent.py, investigation_service.py) is a straightforward extension of this core once you have it — see the Learning Roadmap (Section 19) for when to read those.

Folder responsibilities, one line each:

  • routers/ — HTTP-only. Parse the request, call exactly one service function, return a response model. No business logic, no direct DB queries (models.py is the one exception — it reads YAML directly since there's no service layer worth adding for a single config passthrough).
  • schemas/ — Pydantic models only. Every field here is either an LLM output shape (RoutingDecision), an internal result type (RoutingResult), or an HTTP contract (ChatResponse). No methods beyond what Pydantic gives you for free.
  • services/ — where all the actual logic lives. Every service is either a plain function module (decision_service, analytics_service, routing_learning, routing_agent, history_service, stats_service — no instance state) or a thin class with @lru_cached construction (ClassifierService, RoutingEngine, QualityVerifier — hold config loaded once at construction).
  • services/providers/ — the one place polymorphism is actually used in this codebase. See Section 12.
  • database/ — SQLAlchemy setup and the 9 table definitions. No query logic lives here; that's in services/.
  • utils/ — cross-cutting concerns: env config, YAML config, startup validation, logging. Nothing here depends on services/ or routers/.

3. File-by-File Walkthrough

backend/main.py

Purpose: FastAPI app construction, lifespan() startup hook, router registration, /health. Why it exists: Every FastAPI app needs exactly one of these. Who calls it: Uvicorn (uvicorn backend.main:app). What it calls: validate_startup_config(), configure_logging(), get_settings(). Important methods: lifespan() — an @asynccontextmanager that runs validate_startup_config() before yield (blocks boot on bad config) and does nothing on shutdown. Common mistakes: Assuming Base.metadata.create_all() runs here — it doesn't. Schema creation is scripts/bootstrap_db.py, run explicitly. If you add a new table and forget to run bootstrap against a fresh DB, you'll get a no such table error at first query, not at boot. Interviewer question: "Why does startup validation block boot instead of just logging a warning?" — answer is in the file's own docstring: a broken tier should fail at deploy time, not on the first request that happens to hit it.

backend/routers/chat.py

Purpose: POST /chat — the entire user-facing pipeline in one function. Why it exists: This is the product. Who calls it: The Streamlit frontend via httpx. What it calls: classifier.classify(), engine.select(), get_provider() → provider.generate(), estimate_cost(), quality_verifier.verify(), decision_service.record() / decision_service.record_failure(). Important methods: chat() — the only function in the file. FastAPI dependency injection (Depends(get_db), Depends(get_settings), etc.) supplies a fresh Session and cached service singletons per call. Common mistakes: Assuming classification and routing selection can fail and get audited like the provider call — they can't and don't (see Section 13: an exception in classifier.classify() or engine.select() is uncaught, on purpose). Also: assuming there's a retry on provider failure — there isn't. One call, one shot, 502 on failure. Interviewer questions: "Walk me through what happens if quality_verifier.verify() raises." (It can't reach the caller — see quality_verifier.py, it catches everything internally and returns None.) "Why is quality_verifier only called for BASIC/STANDARD?" (Comment in the file: nothing to compare ADVANCED against, it's already the best model.)

backend/schemas/routing_decision.py

Purpose: RoutingDecision (exact JSON shape demanded from the classifier LLM) and RoutingDecisionOutcome (that decision plus operational metadata: latency, cost, fallback_used). Why two layers: RoutingDecision is what the LLM must produce and RoutingDecision.model_validate(data) is what actually turns untrusted LLM JSON into a typed object your code can trust. RoutingDecisionOutcome wraps it with metadata the LLM never produces. Who calls it: classifier_service.py produces both; chat.py and decision_service.py consume them. Common mistake: Assuming task_type/reasoning_level drive routing logic — they don't. Only routing_tier and confidence do (see routing_engine.py). task_type is captured for analytics only.

backend/services/classifier_service.py

Purpose: Ask a cheap LLM (configured under routing.yaml's classifier: block — currently mistralai/mistral-small-3.2-24b-instruct via OpenRouter) to classify a prompt into a tier, with a heuristic fallback. Why it exists: Routing needs *some* signal about prompt complexity before picking a model; an LLM classifier is more accurate than a word-count heuristic, so it's the primary path. Who calls it: chat.py via the classify FastAPI dependency. What it calls: providers.factory.get_provider(), heuristic_classifier.classify_heuristically() (fallback only), cost_estimator.estimate_cost(). Important methods:

  • classify(prompt) — public entrypoint. Try/except around

_classify_with_llm; catches literally Exception (see the # noqa: BLE001 comment — deliberate, any failure here must degrade, not crash).

  • _classify_with_llm(prompt) — builds the classifier prompt, calls the

provider with response_format="json_object", parses and validates the JSON via RoutingDecision.model_validate.

  • strip_json_fence(text) — module-level helper (also reused by

quality_verifier.py), defensively strips a `json fence even though response_format="json_object" is what actually fixes this in practice (see its own docstring — verified against a real bug where Mistral wrapped JSON in a fence). Common mistakes: Assuming a classifier failure ever surfaces as a user- facing error — it can't; it silently degrades to the heuristic path with fallback_used=True in the response. Assuming the classifier answers the user's prompt — it never does; its only job is picking a tier. Interviewer questions: "What happens if google_api_key/ openrouter_api_key isn't set?" (self._client_ready = bool(api_key) — if false, classify() raises RuntimeError internally and falls straight to heuristic, no network call attempted.) "Why @lru_cache on get_classifier_service()?" (One instance per process — same pattern as get_settings() — the constructor does I/O, reading routing.yaml.)

backend/services/heuristic_classifier.py

Purpose: Word-count-based fallback tier decision. Why it exists: Explicitly documented in the module docstring as "the exception path, not the primary classifier" — degrade gracefully instead of 500ing when the LLM classifier is unavailable. Important detail — a real bug that was fixed here: the fallback's confidence used to be hardcoded to 0.5, which sits *below* routing.yaml's confidence_thresholds.low (0.6). Since routing_engine.select() escalates any decision under low, every single fallback got silently bumped one tier — a 5-word prompt landing on BASIC by word count would get pushed to STANDARD purely because 0.5 < 0.6, an interaction nobody intended. Fixed by _fallback_confidence(): derives confidence as low + 0.05 (capped below high), so the heuristic tier is trusted and *not* auto-escalated. This is a genuinely good "why was this done" story for Section 15 and a strong debugging interview question. Interviewer question: "If confidence_thresholds.low in routing.yaml were changed to 0.8, what would _fallback_confidence() return, and would that still avoid the escalation bug?" (Reason through min(low + 0.05, high - 0.01).)

backend/services/routing_engine.py

Purpose: Turn a RoutingDecision into a concrete RoutingResult (provider, model, max_output_tokens), applying confidence-based escalation. Why it exists: Deliberately knows nothing about model names — only tiers. Swapping which model serves ADVANCED is a one-line routing.yaml edit; this file never changes for that. Important methods:

  • select(decision) — reads confidence_thresholds from the cached YAML

config; if escalate_on_low_confidence and decision.confidence < low, calls _next_tier() and bumps one tier (never past ADVANCED — see _next_tier returning None at the top of _TIER_ORDER).

  • _next_tier(tier) — index lookup into `_TIER_ORDER = [BASIC, STANDARD,

ADVANCED]. Common mistake: Assuming escalation can happen more than once per request — it can't; select() only ever bumps zero or one tier, never recursively re-checks the new tier's own confidence (there isn't a new confidence to check — it's the same decision.confidence throughout). Interviewer question: "A request classifies as ADVANCED with confidence 0.4. What tier does it actually route to?" (Still ADVANCED — _next_tier(ADVANCED) returns None, so candidate is None` and no escalation happens, despite low confidence. This is a real edge case worth knowing.)

backend/services/providers/*

See Section 12 for the deep dive. Summary here: base.py defines LLMProvider (ABC, one abstract method generate()) and ProviderResponse (normalized {text, input_tokens, output_tokens}). factory.py is an if/if/raise — not a registry, not a class, "ceremony for two providers" per its own docstring. gemini_provider.py wraps google.generativeai.GenerativeModel. openrouter_provider.py wraps a single httpx.post to one REST endpoint that fronts Mistral/DeepSeek/etc.

backend/services/decision_service.py

Purpose: The single write path for a successful request (record()), the single write path for a failed one (record_failure()), and read-side reconstruction of a DecisionCard (get_decision_card()). Why it exists: Centralizing every write to requests / routing_decisions / execution_results / quality_results in one function means there's exactly one place that can get the transaction boundary wrong, and it's been gotten right. Important methods:

  • record(...) — inserts Request, then db.flush() (critical — see

the comment: no ORM relationship() exists between the tables, only column-level ForeignKeys, so nothing else orders these inserts; SQLite silently tolerated the unflushed case in dev, Postgres/Supabase raised a real ForeignKeyViolation during migration), then inserts RoutingDecision, ExecutionResult, and conditionally QualityResult, then one db.commit() for all four.

  • record_failure(...) — inserts one FailedRequest row. Wrapped in its

own try/except that must never raise (it's called from inside exception handlers); on failure it rolls back and logs at CRITICAL rather than propagating.

  • get_decision_card(db, request_id) — three-way join

(Request/RoutingDecision/ExecutionResult), builds reasoning_steps deterministically from stored columns (_build_reasoning_steps), and looks up a matching OptimizationRecommendation by exact attribute equality (_find_matching_recommendation) — not a foreign key. Common mistakes: Assuming DecisionCard is stored anywhere — it isn't; it's reconstructed from relational columns on every read (explicit design choice, see the module docstring: storing it as a JSON blob "would duplicate the same facts twice with no independent value"). Assuming a quality_results row always exists — it's optional (outerjoin in history_service.py, conditional insert here); ADVANCED-tier requests never get one. Interviewer questions: "Why db.flush() and not just db.commit() immediately after adding Request?" (Flush assigns the PK and makes the row visible to the transaction's subsequent FK-checked inserts without ending the transaction — a partial commit would break atomicity.) "What happens if record() itself raises after record_failure already ran for a provider error?" (It can't — they're mutually exclusive branches in chat.py's try/except structure; record_failure for stage="persistence" only runs if record() itself throws.)

backend/database/models.py

Covered table-by-table in Section 9. Read the module docstring closely — it explains *why* the schema is 9 normalized tables instead of one flat log, and calls out that requests → {routing_decisions, execution_results, quality_results} are column-level FKs with no ORM relationship().

backend/utils/yaml_config.py

Purpose: load_routing_config() / load_pricing_config(), both @lru_cached. Why it exists: Routing policy and pricing are business rules meant to change without a Python deploy. Critical operational detail: because these are lru_cached at module level, a running process never sees a routing.yaml/pricing.yaml edit until restart. There is no file-watcher, no cache-busting endpoint. Editing the YAML and expecting the next request to pick it up without a restart is a common mistake new engineers make on this codebase. Interviewer question: "You edited routing.yaml's advanced tier model and curl'd /chat — the old model is still being used. Why?" (lru_cache — the process needs a restart.)

backend/utils/startup_validation.py

Purpose: validate_startup_config() — collects *every* config problem into one error, not just the first one found, and raises StartupConfigError to block boot. What it actually checks: every tier's provider is in {"google", "openrouter"}; every tier's model has a pricing.yaml entry; max_output_tokens is a positive int per tier; confidence_thresholds.low < high, both in [0, 1]; learning.min_sample_size is a positive int; learning.min_confidence is in [0, 1]; policy_version is present. What it does NOT check: anything about API keys being valid (only that .env parses — a wrong-but-present API key still boots fine and fails at first real request), anything about the *classifier*'s specific fields beyond provider/model/max_output_tokens (no threshold checks on the classifier block beyond what's shared with tiers).

tests/conftest.py and tests/test_failure_paths.py

Purpose: db_session fixture — fresh in-memory SQLite per test, via StaticPool connect args for thread-safety with FastAPI's TestClient. test_failure_paths.py monkeypatches the provider/classifier/quality- verifier dependencies with fakes (_RaisingProvider, _WorkingProvider, _FakeClassifier, _FakeQualityVerifier) to deterministically exercise every failure branch in chat.py without real API calls — this is your reference for "how do I test a route that calls three external LLM APIs without a network."

5. Function Walkthrough — decision_service.record()

Purpose: Persist all four rows for one successful request in a single transaction. Inputs: db: Session, plus every field of the eventual response (request_id, prompt, response, decision_outcome, routing_result, total_latency_ms, token counts, total_cost, provider_success, error_message, quality_verdict). Outputs: None — this is a pure side-effecting write. Side effects: Four INSERTs (Request, RoutingDecision, ExecutionResult, conditionally QualityResult) and one COMMIT. Exceptions: Any SQLAlchemy exception (constraint violation, connection loss) propagates uncaught to the caller (chat.py's try/except), which converts it to record_failure(stage="persistence") + HTTP 500. Database writes: Exactly as above — no reads. Configuration reads: load_routing_config().get("policy_version", "v1.0") — every RoutingDecision row is stamped with the currently active policy version. External API calls: None — this function is pure DB I/O. Complexity: O(1) — four fixed inserts regardless of input size. Dependencies: backend.database.models (four ORM classes), backend.utils.yaml_config.load_routing_config.

6. Execution Trace — one POST /chat request, end to end

Prompt: "Explain the CAP theorem in distributed systems".

  1. routers/chat.py: chat() receives ChatRequest(prompt=...).

prompt = body.prompt.strip(). request_id = str(uuid.uuid4()), e.g. "a1b2c3...". start = time.perf_counter().

  1. classifier.classify(prompt) is called.

ClassifierService.classify() tries _classify_with_llm(prompt): builds a JSON-only prompt via _build_classifier_prompt(), calls OpenRouterProvider.generate() against mistralai/mistral-small-3.2-24b-instruct with response_format="json_object". Say the model returns {"routing_tier": "STANDARD", "task_type": "Explanation", "reasoning_level": "Medium", "confidence": 0.82, "reason": "..."}. json.loads() + RoutingDecision.model_validate() succeed. No fallback needed. Returns RoutingDecisionOutcome(decision=..., cost=~$0.0001, fallback_used=False).

  1. engine.select(decision) is called. confidence_thresholds.low is

0.6; 0.82 >= 0.6, so no escalation. tier_config = self._config["tiers"]["standard"] → {provider: openrouter, model: mistralai/mistral-small-3.2-24b-instruct, max_output_tokens: 1536, reasons: [...]}. Returns RoutingResult(provider="openrouter", model="mistralai/mistral-small-3.2-24b-instruct", tier=STANDARD, escalated=False, ...).

  1. get_provider("openrouter", settings) returns an

OpenRouterProvider instance (constructed fresh per call — no caching at this layer, unlike ClassifierService).

  1. provider.generate(prompt, model, max_tokens=1536) — a real

httpx.post to https://openrouter.ai/api/v1/chat/completions, no response_format this time (regular chat answer, not structured output). Returns ProviderResponse(text="CAP theorem states...", input_tokens=12, output_tokens=340).

  1. estimate_cost("mistralai/mistral-small-3.2-24b-instruct", 12, 340)

— reads pricing.yaml: input_per_million=0.10, output_per_million=0.30. (12/1e6)*0.10 + (340/1e6)*0.30 = 0.0000012 + 0.000102 = 0.0001032, rounded to 8 decimals.

  1. total_cost = round(model_cost + decision_outcome.cost, 8) — sums

the classifier's own tiny cost with the answer model's cost. total_latency_ms = round((time.perf_counter() - start) * 1000, 2).

  1. Tier check: routing_result.tier != RoutingTier.ADVANCED is True

(it's STANDARD), so quality_verifier.verify(prompt, answer) runs — another OpenRouter call, this time to the same Mistral model as judge, asking {"passed": true|false, "reason": "..."}". Say it returns QualityVerdict(passed=True, reason="Correctly explains CAP theorem").

  1. decision_service.record(...) — inside one transaction: `INSERT

requests (prompt, response, normalized_prompt, prompt_hash = SHA-256 of the normalized prompt), db.flush(), INSERT routing_decisions (classifier_tier=STANDARD, final_tier=STANDARD, confidence=0.82, task_type="Explanation", selected_provider="openrouter", selected_model="mistralai/...", routing_policy_version="v1.0", escalation_reason=None), INSERT execution_results (latency, token counts, estimated_cost=total_cost), INSERT quality_results (verdict=True, reasoning), db.commit()`.

  1. Response construction: chat() builds and returns ChatResponse

with every field pulled from the objects computed in steps 2–9 — no additional DB read, everything is still in memory from the pipeline that just ran.

  1. Nginx forwards the JSON to Streamlit, which renders the answer plus

the routing metadata panel (tier, provider, model, cost, confidence).

No retries occurred anywhere in this trace. No caching occurred anywhere in this trace (aside from the lru_cached YAML/config singletons, which are per-process, not per-request). No background task or queue was involved — step 9's commit happens synchronously, in-request, before the HTTP response is returned.

7. Variable Journey — prompt

flowchart LR
    A["body.prompt<br/>raw ChatRequest field"] --> B["prompt = body.prompt.strip()<br/>chat.py"]
    B --> C["classifier prompt<br/>_build_classifier_prompt(prompt)<br/>wraps the SAME string in a routing instruction"]
    B --> D["provider prompt<br/>passed unmodified to provider.generate()<br/>as the actual chat prompt"]
    B --> E["normalized_prompt<br/>decision_service._normalize_prompt()<br/>= ' '.join(prompt.lower().split())"]
    E --> F["prompt_hash<br/>sha256(normalized_prompt).hexdigest()"]
    B --> G["requests.prompt column<br/>stored verbatim, NOT normalized"]
    D --> H["provider_response.text<br/>the model's answer, a DIFFERENT variable"]
    H --> I["quality_verifier prompt<br/>_build_verdict_prompt(prompt, response)<br/>original prompt reused again, third time"]

The same in-memory string prompt is reused three separate times as input to three separate LLM calls (classifier, answer generation, quality judge) — it is never mutated, only wrapped in different instruction templates. normalized_prompt and prompt_hash are the only derived forms, and they exist purely for future duplicate-detection/analytics use (nothing in the current codebase queries prompt_hash — it's indexed but unused beyond storage; a fair thing to flag as unused infrastructure in Section 16).

10. Configuration Walkthrough

.env → Settings: backend/utils/config.py's Settings(BaseSettings) reads .env via pydantic-settings. get_settings() is @lru_cached — parsed once per process. Fields: google_api_key, openrouter_api_key, database_url, log_level, easy_max_words, medium_max_words.

routing.yaml/pricing.yaml → cached dicts: backend/utils/yaml_config.py's load_routing_config() / load_pricing_config(), both @lru_cached, both reading straight off disk via yaml.safe_load(). Never reloaded during the life of a process — this is the single most important operational fact about this codebase's config system. Change routing.yaml, and every running worker keeps using the old values until restarted. There is no /admin/reload-config endpoint, no file-watcher, no TTL.

Who reads what:

  • Settings → database/db.py (connection string), providers/factory.py

(API keys), heuristic_classifier.py (word thresholds), main.py (log level).

  • routing.yaml → routing_engine.py (tiers, thresholds),

classifier_service.py (classifier provider/model), quality_verifier.py (judge model — reuses the classifier's config block), routing_learning.py / routing_agent.py (min_sample_size), decision_service.record() (policy_version stamp), routers/models.py (read-only passthrough).

  • pricing.yaml → cost_estimator.py only, plus

startup_validation.py cross-checking every configured model has a pricing entry.

Startup validation order: main.py's lifespan() calls validate_startup_config() *before* the app starts serving. If it raises, the process never comes up — no partial availability.

11. Service Deep Dive — routing_learning.py

Responsibilities: Recompute routing_patterns from raw history; generate optimization_recommendations by comparing each tier's *currently configured* model against better-performing alternatives. Collaborators: query_helpers.PASS_RATE (shared SQL fragment), utils.yaml_config.load_routing_config (for min_sample_size and the current tier config). Internal workflow: One grouped query over routing_decisions JOIN execution_results OUTER JOIN quality_results, grouped by (task_type, task_subcategory, provider, model, tier, policy_version). Wholesale DELETE + reinsert into routing_patterns. Then _generate_recommendations(): for each (task_type, tier) under the *current* policy_version only, find the pattern matching the currently-configured (provider, model), then look for candidate patterns with sample_size >= min_sample_size and a strictly higher pass_rate; pick the single best one; build one OptimizationRecommendation. Public methods: refresh(db) -> RefreshResult. Private methods: _generate_recommendations(), _build_recommendation(). Important algorithm detail: recommendations are restricted to the current policy_version on purpose — comparing across policy epochs would compare a pattern against a model config that's no longer even active, producing a "recommendation" the current policy never earned. This is explicitly called out in the function's docstring. Potential improvements (from the code's own comments, not invented): the module docstring flags this as O(n) full-table scan on every refresh, fine at current scale, and suggests an incremental upsert keyed by the same group columns if routing_decisions grows into the hundreds of thousands of rows.

factory.get_provider(name, settings) is a plain function with an if name == "google": ... if name == "openrouter": ... raise ValueError body — explicitly *not* a registry pattern or a Factory class, per its own docstring ("ceremony for two providers"). This is dependency inversion in its simplest possible form: every caller (chat.py, classifier_service, quality_verifier) depends on the LLMProvider interface, never on GeminiProvider/OpenRouterProvider directly. Polymorphism happens at exactly one call site per caller: provider.generate(...) — the caller never branches on which concrete class it holds. Adding a third provider means writing one new class satisfying LLMProvider and adding one line to factory.py's if chain; zero changes required in chat.py, routing_engine.py, classifier_service.py, or quality_verifier.py.

13. Error Handling Walkthrough

flowchart TD
    A["POST /chat"] --> B["classify() / select()"]
    B -->|"exception here"| B1["UNCAUGHT -> HTTP 500 with traceback<br/>(deliberate: this is a programming bug,<br/>not a degraded external dependency —<br/>see chat.py's module docstring)"]
    B --> C["provider.generate()"]
    C -->|exception| C1["record_failure(stage=provider_call) -> HTTP 502"]
    C -->|ok| D["estimate_cost()"]
    D -->|exception, e.g. model not in pricing.yaml| D1["record_failure(stage=cost_estimation) -> HTTP 502"]
    D -->|ok| E["quality_verifier.verify()"]
    E -->|"exception INSIDE verify()"| E1["caught internally, returns None<br/>— never reaches chat.py"]
    E --> F["decision_service.record()"]
    F -->|exception| F1["record_failure(stage=persistence) -> HTTP 500"]
    F -->|ok| G["200 ChatResponse"]

Validation errors: Handled by FastAPI/Pydantic before chat() ever runs — ChatRequest.prompt has min_length=1, max_length=8000; a violation is an automatic HTTP 422, never reaches application code.

Provider errors: Caught in chat.py, logged, recorded via record_failure(stage="provider_call"), re-raised as HTTP 502.

Database failures: Caught around decision_service.record() in chat.py; record_failure itself has its own inner try/except that must never raise (it's called from an exception handler) — a failure to write the failure record is logged at CRITICAL and swallowed, not re-raised, since re-raising here would mask the original error the caller is trying to report.

Configuration failures: Caught nowhere at request time by design — startup_validation.py is meant to catch these at boot, before the app ever serves a request that could hit a bad config path.

HTTP exceptions: HTTPException(status_code=502, ...) / HTTPException(status_code=500, ...) / HTTPException(status_code=404, ...) (in decisions.py, agent.py) — FastAPI converts these to the matching HTTP response.

Rollback behaviour: record_failure() calls db.rollback() *before* inserting the FailedRequest row — this discards any partial state from whatever failed mid-transaction before writing the audit record on a clean session.

Failure recording — the one gap: an exception during classification or routing selection itself is *not* recorded as a failed_requests row. chat.py's own module docstring explains why: those are pure, in-process logic with no external call that can legitimately fail — an exception there is a real bug, not a degraded dependency, and should surface as a 500 with a full traceback rather than be silently swallowed into an audit row that implies "an external thing failed."

15. Engineering Decisions

Why a normalized database (4+ tables) instead of one flat log table? Historical analytics and policy comparison (PR2/PR3, per the models.py docstring) need to query "just the routing decision" or "just the cost" without scanning a denormalized blob. One row per lifecycle stage means a query about that stage touches exactly the table it needs.

Why provider abstraction for exactly two providers? Cheap insurance — one interface, two implementations, zero cost today, and a third provider later is one new file, not a refactor of chat.py/routing_engine.py.

Why routing.yaml instead of hardcoded tier→model mapping in Python? Routing policy is a business decision (which model handles which complexity tier) that changes independently of code — a YAML edit + restart vs. a full deploy cycle.

Why is the learning system advisory-only (never auto-applies a recommendation)? routing.yaml's own comment on the learning: block is explicit: neither min_sample_size/min_confidence nor apply_recommendations ever changes what routing.yaml's tiers route to — only a human bumping policy_version does. This is a deliberate "human-in-the-loop" safety choice for a system making cost/quality trade-offs — auto-applying a recommendation based on a possibly-small or stale sample could silently degrade answer quality with no review step.

Why is the Routing Optimization Agent deterministic SQL, not an LLM reasoning loop? routing_agent.py's module docstring states this directly: an LLM would add cost, latency, and a chain-of-thought exposure risk for a job five SQL queries already do exactly and reproducibly. The five checks (_find_degraded_task_types, _find_expensive_task_type, _detect_cost_anomaly, _compare_policy_versions, _validate_recommendations) are all fixed-threshold arithmetic over existing tables — "agentic" here means "a fixed, inspectable pipeline," not "an LLM deciding what to check next."

Why does _validate_recommendations re-query live tables instead of trusting routing_patterns? routing_agent.py's _live_stats() docstring explains: routing_patterns is only as fresh as the last POST /analytics/refresh, but live traffic keeps accumulating in routing_decisions in the meantime. Re-deriving straight from the raw tables makes validation meaningful rather than circular — checking a recommendation against fresh reality, not against the same snapshot it was generated from.

Why is DecisionCard reconstructed on every read instead of stored? decision_service.py's module docstring: storing it as a parallel JSON blob "would duplicate the same facts twice with no independent value" — routing_decisions + execution_results (joined) are the single source of truth.

16. Code Smells

  • prompt_hash is written but never read. decision_service._prompt_hash()

computes and indexes a SHA-256 hash on every request, but no query in the codebase (checked every service file) ever filters or joins on it. It reads like planned-but-unbuilt duplicate-detection infrastructure.

  • failed_requests has no read endpoint. Every failure is faithfully

recorded, but there's no GET /failures router — the audit trail exists only for someone to query the database directly. If failure visibility matters for on-call, this is the gap.

  • **routing_policies is written once by bootstrap_db.py and never read

back at runtime.** It's seeded audit data with no current consumer in backend/ — likely intended for a future "which policy was active on date X" view that doesn't exist yet.

  • **O(n) full scans in routing_learning.refresh() and every finding

function in routing_agent.py.** Explicitly acknowledged as fine at current scale in the code's own comments — flagged here per the module's own admission, not a new discovery.

  • decision_service.py mixes an import in the middle of the file

(logger = logging.getLogger(__name__) sits between the model imports and the schema imports, breaking the usual all-imports-at-top convention) — cosmetic, but worth a quick cleanup if you're already editing this file.

  • **history_service.py's HistoryItem construction hardcodes

reasoning_level="", classifier_model="", classifier_cost=0.0, fallback_used=False** — these fields exist on ChatResponse but aren't persisted anywhere per-request (no RoutingDecision column captures them), so history reconstructs them as empty/default rather than real values. Not a bug — HistoryItem's schema currently promises fields the stored data can't actually supply.

  • No coupling problems worth flagging beyond the above — the read/write

service split (Section 14) keeps most of the codebase cleanly separated.
